### Decision: **keep our own pgvector pipeline** (ADR-017)

1. **Tenant isolation is already designed for it.** Chunks live in our shared schema with `organizationId` filters
   enforced in `PgVectorStore`; the security model's tenant rules apply unchanged. A Bedrock KB would need
   per-tenant KBs or metadata filtering, and a new isolation review.
2. **No extra store.** KB needs Aurora PostgreSQL / OpenSearch / S3 Vectors; our RDS PostgreSQL is not a listed
   store. Adopting KB would add a second always-on data service (cost + operations) for no capability we lack.
3. **Not AWS-locked.** The pipeline works with any embedding provider behind `AiProvider.embed` (OpenAI, Titan,
   Cohere), runs locally in Docker, and moves between clouds.
4. **Bedrock still contributes the model side**: embeddings through Titan/Cohere via the provider adapter.

**Revisit when:** customers need SharePoint/Confluence/Drive connectors with document-level ACL sync; retrieval
quality work (reranking, multimodal) outweighs the lock-in; or the corpus outgrows a single PostgreSQL instance.
Then add KB **behind** `KnowledgeSearcher` as an alternative searcher, not a replacement.

### Three different kinds of "routing" - do not confuse them

| Kind                        | Question it answers                                                                        | AWS feature(s)                                                                                                                                                                      | Our equivalent                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Model-inference routing** | "Which model / which region serves this prompt?"                                           | **Intelligent Prompt Routing** (per-prompt choice between models of one family), **cross-region inference profiles** (which region), Gateway "model-based routing across providers" | `ProviderResolver` + per-agent `providerConfigId`/`model`; `AiProvider` adapters |
| **Gateway routing**         | "How does an agent reach tools / other agents / LLM endpoints, with what auth and policy?" | **AgentCore Gateway** (+ Policy, Identity)                                                                                                                                          | `ToolRegistry` + `ToolExecutor` permission layer (ADR-010); outbound SSRF guard  |
| **Agent orchestration**     | "Who runs the think-act loop, enforces budgets and persists steps?"                        | **You** (framework in your container hosted on Runtime) or the managed **Harness**                                                                                                  | `AgentRunner` (budgets, delegation, step persistence)                            |

### Intelligent Prompt Routing (Doc-verified, [prompt-routing](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.html), 2026-11-10)

Single serverless endpoint that predicts which model **in the same family** answers a prompt best and routes
there, with a fallback model and a configurable "response quality difference" threshold. Default routers use
select **Amazon Nova** and **Meta Llama** models; region-dependent. Limitations stated: optimised for **English**
only, cannot learn from your own performance data. The page does **not** say whether it is preview or GA and has no
pricing. **Not Claude-family** per the model table on the page, so it cannot route our default Claude agents.
**Decision: not used.** Our routing is explicit and auditable per agent; unpredictable per-prompt model switching
complicates cost attribution (`AI_PRICING_JSON` is keyed by model id) and evaluation.

## 4. Quotas to check before going beyond a demo

Open **Service Quotas -> Amazon Bedrock** in the region you use (or `aws service-quotas list-service-quotas --service-code bedrock --region <region>`), and read the "Quotas for the `bedrock-runtime` endpoint" page. Check at least:

- On-demand **tokens per minute** and **requests per minute** for each chat model you enable (separate per model and per region; cross-region/global profiles have their own entries).
- **Requests per minute for each embedding model** (embeddings are RPM-throttled, and Titan V2 takes one text per request, so a bulk ingestion of N chunks is N requests).
- Concurrent / max tokens per request, and the Anthropic first-use form status.
- Non-Bedrock limits the stack touches: Fargate vCPU quota, Elastic IPs (one per NAT gateway), VPC and ALB limits, ENIs in private subnets, RDS instance count, ElastiCache nodes.
- AgentCore service quotas, if you ever adopt it (not read here: **Could not verify**).

Your account's values may be **lower** than documented defaults (account age, usage history); quota increases are not automatic.
