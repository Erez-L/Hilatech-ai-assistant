א. פתיחה ואבטחה של החשבון

1

פתיחת חשבון AWS

חינם
  1. היכנס ל-aws.amazon.com ובחר Create an AWS Account. השתמש בתיבת מייל של העסק שתישאר אצלך (למשל aws-root@your-domain), לא בתיבה אישית. שם החשבון: hilatech.
  2. הוסף כרטיס אשראי, אמת מספר טלפון ובחר בתוכנית התמיכה Basic (חינם).
  3. התחבר כ-Root user עם אותו מייל.
צפוימגיעים לדף הבית של הקונסולה.
מה יכול להשתבשאימות הכרטיס נכשל (צריך כרטיס שמאשר עסקאות בינלאומיות באינטרנט). הפעלת החשבון יכולה לקחת כמה דקות ועד יום: חכה למייל ה-welcome.
2

נעילת משתמש ה-root

חינם
  1. בתפריט החשבון (למעלה) בחר Security credentials, אחר כך Multi-factor authentication (MFA) ו-Assign MFA device. עדיף passkey או מפתח אבטחה, וגם אפליקציית אימות בסדר. רשום שני מכשירי MFA אם אפשר, ושמור את פרטי השחזור מחוץ למחשב.
  2. אל תיצור access keys ל-root.
  3. מכאן והלאה לא משתמשים ב-root, חוץ מפעולות שרק הוא יכול לבצע (שינוי תוכנית תמיכה, סגירת החשבון).
צפויב-Security credentials מופיע "MFA device: assigned".
מה יכול להשתבשאובדן מכשיר ה-MFA בלי מכשיר שני מחייב תהליך שחזור מול התמיכה של AWS.
3

התראות תקציב, לפני הכול

חינם
  1. חפש Billing and Cost Management, בתפריט בחר Budgets ואז Create budget.
  2. בחר Use a template (simplified) ואז Monthly cost budget. שם: account-monthly. סכום: לפי הסבולת שלך (התחל נמוך). הזן את המייל שלך וצור.
  3. ב-Billing preferences סמן Receive AWS Free Tier alerts ושמור.
  4. ב-Account settings גלול ל-IAM user and role access to Billing information, לחץ Edit ואז Activate IAM Access. בלי זה משתמש הניהול משלב 4 לא יראה חיובים.
  5. ב-Cost Anomaly Detection צור מוניטור ל-"AWS services" עם התראה במייל (חינם).
צפויתקציב ברשימה בסטטוס OK.
חשובתקציב הוא התראה ולא מגבלה, ונתוני העלות מתעדכנים באיחור של שעות. הוא לא יעצור משאב שרץ בלי שליטה.
4

IAM Identity Center ומשתמש ניהול

חינם

בלי משתמשי IAM ובלי מפתחות ארוכי טווח.

  1. בחר בקונסולה את האזור הראשי שלך (ראה שלב 7). ל-Identity Center קשה לשנות אזור אחר כך.
  2. חפש IAM Identity Center ולחץ Enable. אם נשאלת, הפעל עם AWS Organizations (חינם).
  3. ב-Settings, תחת Authentication, הגדר MFA: "Every time they sign in".
  4. ב-Users לחץ Add user והזן שם ומייל. תקבל הזמנה במייל: אשר, קבע סיסמה ורשום MFA.
  5. ב-Permission sets צור permission set מסוג Predefined בשם AdministratorAccess, עם session של 4 שעות.
  6. ב-AWS accounts בחר את החשבון, לחץ Assign users or groups, בחר את המשתמש שלך ואת AdministratorAccess.
  7. רשום את כתובת ה-AWS access portal, בצורת https://d-xxxxxxxxxx.awsapps.com/start.
צפויפתיחת כתובת הפורטל מציגה את החשבון עם קישור AdministratorAccess.
מה יכול להשתבשמייל ההזמנה נוחת בספאם. כתובת הפורטל תלויה באזור. האזור של Identity Center לא מגביל היכן מריצים את המערכת.

ג. אזור ו-Bedrock

7

בחירת אזור

חינם

בחר אזור אחד ל-dev. השיקולים לפי הסדר: זמינות המודלים שאתה רוצה, דרישות פרטיות ומיקום נתונים (לקוחות באירופה מחייבים אזור אירופי), השהיה ומחיר. ברירות מחדל סבירות: us-east-1 (הכי הרבה מודלים) או eu-central-1 (אירופה, קרוב לישראל). לא הצלחתי לאמת איזה מודל זמין באיזה אזור, ולכן בדוק בחשבון שלך:

export AWS_REGION=<REGION, e.g. us-east-1>
# Models that can be called on-demand in this region:
aws bedrock list-foundation-models --region $AWS_REGION \
  --query 'modelSummaries[].{id:modelId,provider:providerName,io:outputModalities[0],inference:inferenceTypesSupported}' --output table
# Inference profiles (newer Claude models usually need one of these ids):
aws bedrock list-inference-profiles --region $AWS_REGION \
  --query 'inferenceProfileSummaries[].inferenceProfileId' --output text | tr '\t' '\n' | sort

רשום שלושה מזהים: מודל צ'אט זול (למשל מודל Amazon Nova), מזהה של Claude אם אתה רוצה Claude, ו-amazon.titan-embed-text-v2:0 ל-embeddings. השתמש במזהים בדיוק כפי שהודפסו אצלך, לא במזהים שברשימה בקוד, שאינם מאומתים.

מה יכול להשתבשAccessDeniedException: לפרופיל אין הרשאות Bedrock. רשימה ריקה: Bedrock לא זמין באזור הזה, בחר אחר. אם בחרת אזור שאינו us-east-1, הגדר אותו בעקביות ב-AWS_REGION ובפרופיל ה-CLI.
8

גישה למודלים של Bedrock

עלות קטנה

ברוב האזורים רוב המודלים נפתחים בשימוש הראשון. מודלים של Anthropic (Claude) דורשים טופס חד-פעמי.

  1. בקונסולה פתח Amazon Bedrock (ודא את האזור למעלה), בחר Model catalog, פתח מודל של Anthropic ומלא את טופס פרטי השימוש: תיאור החברה או הפרויקט וכתובת אתר (גם GitHub או פורטפוליו מתקבלים).
  2. בדוק את הסטטוס:
aws bedrock get-foundation-model-availability --model-id <MODEL_ID> --region $AWS_REGION \
  --query 'agreementAvailability.status' --output text      # AVAILABLE | PENDING | NOT_AVAILABLE | ERROR

הוכח שקריאה אמיתית עובדת מה-CLI:

aws bedrock-runtime converse --region $AWS_REGION --model-id <CHAT_MODEL_OR_PROFILE_ID> \
  --messages '[{"role":"user","content":[{"text":"Say hello in five words."}]}]' \
  --inference-config '{"maxTokens":50}' --query 'output.message.content[0].text' --output text

הוכח ש-embeddings עובדים:

aws bedrock-runtime invoke-model --region $AWS_REGION --model-id amazon.titan-embed-text-v2:0 \
  --content-type application/json --cli-binary-format raw-in-base64-out \
  --body '{"inputText":"hello","dimensions":1024,"normalize":true}' /tmp/titan.json
jq '{dims: (.embedding|length), tokens: .inputTextTokenCount}' /tmp/titan.json     # expect dims 1024
צפוימשפט קצר, ואחר כך dims: 1024.
מה יכול להשתבש
  • AccessDeniedException ... PENDING: הטופס של Anthropic עדיין בטיפול. חכה ובדוק שוב (עד כרבע שעה).
  • on-demand throughput isn't supported: המודל דורש מזהה inference profile (קידומת global., us. או eu.). קח מזהה מ-list-inference-profiles.
  • ThrottlingException בחשבון חדש: מכסות ברירת מחדל נמוכות. בדוק ב-Service Quotas, תחת Amazon Bedrock.

10

הוספת ספק Bedrock בממשק

עלות קטנה
  1. פתח http://localhost:3000 והתחבר עם נתוני ה-seed: owner@demo.local והסיסמה DemoPassw0rd!.
  2. עבור ל-Settings, אחר כך AI, ולחץ Add provider.
  3. Provider: Amazon Bedrock. Name: Bedrock dev. AWS region: האזור שלך, או ריק כדי להשתמש ב-AWS_REGION. אין שדה מפתח ואין שדה כתובת, וזה מכוון.
  4. Default model: הקלד את המזהה המדויק שאימתת בשלבים 7 עד 8. Embedding model: amazon.titan-embed-text-v2:0. סמן Use as the default provider ושמור.
  5. בטבלת הספקים לחץ Check בשורה החדשה.
צפויהתווית הופכת ל-healthy עם זמן תגובה במילישניות.
מה יכול להשתבש
  • המודל לא מוצע ברשימה: לא מזיק, פשוט הקלד את המזהה. הרשימה מסומנת "unverified availability".
  • AWS credentials could not be resolved: ה-session פג, או ש-AWS_PROFILE לא מוגדר לתהליך ה-API.
  • AccessDeniedException: טופס Anthropic בהמתנה, המודל לא פתוח באזור, או שנדרש inference profile.
  • Bedrock לא מופיע בבחירה: AI_BEDROCK_ENABLED=true לא נטען. הפעל מחדש את ה-API.

אחרי שזה עובד, בדוק שיחה אמיתית במסך Assistant, סוכן שמשתמש בכלי, והעלאת מסמך טקסט קטן לבסיס ידע. וקטורי Titan הם באורך 1,024 ומרופדים ל-1,536 באפליקציה, וזה תקין. בזמן בדיקות הגדר maxTokens נמוך.

נקודת עצירהאם הגעת עד כאן והכול עובד, יש לך מערכת עובדת עם Bedrock בעלות של טוקנים בלבד.

ד2

הרשאת Bedrock לשרת

חינם

השרת מקבל תפקיד IAM שמתיר רק קריאה למודלים. כך אין מפתחות AWS על השרת.

cat > /tmp/ec2-trust.json <<'EOF'
{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ec2.amazonaws.com"},"Action":"sts:AssumeRole"}]}
EOF
cat > /tmp/bedrock.json <<'EOF'
{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":["bedrock:InvokeModel","bedrock:InvokeModelWithResponseStream"],"Resource":"*"}]}
EOF
aws iam create-role --role-name hilatech-demo-server --assume-role-policy-document file:///tmp/ec2-trust.json
aws iam put-role-policy --role-name hilatech-demo-server --policy-name bedrock --policy-document file:///tmp/bedrock.json
aws iam create-instance-profile --instance-profile-name hilatech-demo-server
aws iam add-role-to-instance-profile --instance-profile-name hilatech-demo-server --role-name hilatech-demo-server
לדעת"Resource":"*" מתיר כל מודל. אחרי שבחרת מודלים, צמצם ל-ARN שלהם. כל השימוש ב-AI של כל מי שנכנס לדמו מחויב בחשבון שלך.

עולה כסף

בקונסולה: EC2, ואז Launch instance.

  1. Name: hilatech-demo. מערכת הפעלה: Ubuntu Server 24.04 LTS, ארכיטקטורה 64-bit (x86). התמונות נבנות ל-x86, ולכן לא לבחור מכונת Arm (משפחת t4g).
  2. Instance type: t3.medium (2 vCPU, 4GB). מכונה קטנה יותר לא תחזיק את חמשת הקונטיינרים יחד עם PostgreSQL.
  3. Key pair: צור חדש ושמור את קובץ ה-.pem.
  4. Network settings: התר HTTPS ו-HTTP מכל מקום, ו-SSH רק מה-IP שלך (My IP).
  5. Storage: 30GB מסוג gp3.
  6. Advanced details: ב-IAM instance profile בחר hilatech-demo-server. ב-Metadata response hop limit הזן 2. בלי זה הקונטיינרים לא מגיעים לאישורי ה-AWS של השרת, ו-Bedrock ייכשל.
צפויהשרת במצב Running. מכאן הוא מחויב לפי שעה.

גיבוי לילי של המסד ל-S3

עלות קטנה

מהרגע שיש נתונים של לקוח, גיבוי הוא חובה. יוצרים דלי פרטי, מתירים לשרת לכתוב אליו, ומתזמנים גיבוי לילי.

# from your computer
export BUCKET=hilatech-backups-$ACCOUNT
aws s3api create-bucket --bucket $BUCKET --region $AWS_REGION \
  $( [ "$AWS_REGION" != us-east-1 ] && echo --create-bucket-configuration LocationConstraint=$AWS_REGION )
aws s3api put-public-access-block --bucket $BUCKET \
  --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
aws s3api put-bucket-lifecycle-configuration --bucket $BUCKET --lifecycle-configuration \
  '{"Rules":[{"ID":"expire","Status":"Enabled","Filter":{},"Expiration":{"Days":30}}]}'
cat > /tmp/backup.json <<EOF
{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":["s3:PutObject"],"Resource":"arn:aws:s3:::$BUCKET/*"}]}
EOF
aws iam put-role-policy --role-name hilatech-demo-server --policy-name backup --policy-document file:///tmp/backup.json
# on the server
sudo apt-get install -y awscli || sudo snap install aws-cli --classic
cat > /opt/hilatech/backup.sh <<'EOF'
#!/bin/sh
set -eu
cd /opt/hilatech
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
docker compose -f docker-compose.prod.yml exec -T postgres pg_dump -U postgres -Fc hilatech > /tmp/hilatech-$STAMP.dump
aws s3 cp /tmp/hilatech-$STAMP.dump s3://<BUCKET>/postgres/ && rm /tmp/hilatech-$STAMP.dump
EOF
chmod +x /opt/hilatech/backup.sh
( crontab -l 2>/dev/null; echo "15 1 * * * /opt/hilatech/backup.sh >> /var/log/hilatech-backup.log 2>&1" ) | crontab -
/opt/hilatech/backup.sh && aws s3 ls s3://<BUCKET>/postgres/
לדעתהגיבוי מכסה את המסד בלבד. המסמכים שהועלו יושבים על הדיסק של השרת (ה-volume בשם uploads). גיבוי שלא שוחזר אף פעם אינו גיבוי: בצע שחזור ניסיון אחד (שלב פ4) לפני הלקוח הראשון.

דומיין ותעודת TLS

חינם

במצב production ה-API שולח עוגיות עם הדגל Secure, ולכן התחברות עובדת רק ב-HTTPS. בלי תעודה הסביבה לא שמישה.

  1. בקונסולה פתח Certificate Manager (ACM) באזור הפריסה, לחץ Request, בחר תעודה ציבורית לדומיין שלך עם DNS validation.
  2. פתח את התעודה, העתק את רשומת ה-CNAME (שם וערך) וצור אותה אצל ספק ה-DNS שלך.
  3. חכה לסטטוס Issued (דקות) ושמור את ה-ARN:
export CERT_ARN=$(aws acm list-certificates --region $AWS_REGION \
  --query "CertificateSummaryList[?DomainName=='${DOMAIN}'].CertificateArn | [0]" --output text)
echo "$CERT_ARN"
מה יכול להשתבשהתעודה תקועה ב-Pending validation: ה-CNAME הוזן עם סיומת הדומיין פעמיים (הרבה ממשקי DNS מוסיפים אותה לבד) או באזור DNS לא נכון. התעודה חייבת להיות באותו אזור AWS כמו ה-Load Balancer.

חינם

  --thumbprint-list 6938fd4d98bab03faadb97b34396831e3780aea1

{

    "Effect": "Allow",

    }

}
EOF

החשבון שקובע אם יש עסק

עלות לארגון בחודש = (עלות התשתית הקבועה חלקי מספר הארגונים המשלמים) + עלות ה-AI של הארגון + עמלת סליקה.

דוגמה להמחשה, עם מספרים שאינם תחזית: בתשתית production של 470 דולר ו-30 ארגונים משלמים, החלק הקבוע הוא כ-16 דולר לארגון. עם 150 ארגונים הוא יורד לכ-3 דולר, ואז עלות ה-AI הופכת למרכיב העיקרי.

  • נקודת האיזון של ההשקה. אם התוכנית הזולה נמכרת ב-X דולר לחודש, צריך בערך 470 חלקי X ארגונים משלמים רק כדי לכסות את התשתית. זה המספר שכדאי שיהיה בפיילוט לפני שעוברים לשלב 3.
  • ה-AI חייב להיות מתומחר. לכל תוכנית מגדירים מכסת טוקנים חודשית, ומעליה חבילה נוספת בתשלום או עצירה. המנגנון כבר קיים: תקציב לארגון עם עצירה קשיחה.
  • חלופה: לקוח שמביא מפתח משלו (Anthropic או OpenAI) משלם על ה-AI ישירות לספק, ואתה גובה רק על התוכנה. גם זה כבר נתמך.

  4. כיבוי מה שלא בשימוש. שרת הדמו בלילה, סביבת dev בין סבבי בדיקה (cdk destroy).
  5. רמת לוגים. LOG_LEVEL=info ב-production. רמת debug מכפילה את חשבון הלוגים.

הוזלות כשהשימוש יציב (אחרי ההשקה)

  • מעבר ל-Arm (Graviton). Fargate זול בכ-20% על Arm. דורש לבנות את התמונות ל-arm64 ולשנות את cpuArchitecture ב-config.ts. לא נבדק.
  • Savings Plans ו-Reserved Instances. התחייבות לשנה מוזילה את Fargate ואת RDS בעשרות אחוזים. רק אחרי שלושה חודשים של שימוש יציב.
  • מודל זול למשימות פשוטות. סיכומים וסיווגים לא צריכים את המודל היקר. אפשר להגדיר מודל לכל סוכן.
  • VPC endpoints במקום תעבורה דרך NAT, כשהנפח גדל.

מחיקת הכול

עוצר את החיוב

סביבת dev בנויה למחיקה: הדליים ומאגרי ה-ECR מתרוקנים אוטומטית, והמסד נמחק בלי snapshot אחרון. ייצא נתונים קודם אם אתה צריך אותם.

cd infra/cdk
export AWS_PROFILE=hilatech-dev AWS_REGION=<REGION> ENV=dev
npx cdk destroy HilaTech-$ENV-Ops HilaTech-$ENV-App HilaTech-$ENV-Data HilaTech-$ENV-Registry HilaTech-$ENV-Network \
  -c env=$ENV --force

אחר כך נקה את מה ש-CloudFormation משאיר בכוונה:

# Secrets Manager keeps deleted secrets for 30 days, which blocks re-creating the same names:
for s in $(aws secretsmanager list-secrets --include-planned-deletion --region $AWS_REGION \
    --query "SecretList[?starts_with(Name, 'hilatech/${ENV}/')].Name" --output text); do
  aws secretsmanager delete-secret --secret-id "$s" --force-delete-without-recovery --region $AWS_REGION
done
# Anything tagged for this app still alive? (should be empty)
aws resourcegroupstaggingapi get-resources --tag-filters Key=app,Values=hilatech Key=env,Values=$ENV \
  --region $AWS_REGION --query 'ResourceTagMappingList[].ResourceARN' --output text

מחק גם את תעודת ה-ACM ואת רשומות ה-DNS אם לא תשתמש בהן שוב. התקציב ברמת החשבון ו-CDKToolkit יכולים להישאר.

מה יכול להשתבשDELETE_FAILED על ה-VPC בגלל ממשקי רשת שנשארו: חכה כמה דקות ונסה שוב. בדוק למחרת ב-Cost Explorer שהעלות היומית ירדה לאפס בערך. NAT gateway או RDS שנשכחו הם ההפתעה הקלאסית.

החלטות שמחכות לך

  1. AI_BEDROCK_ENABLED לכל סביבה. הקריאות ל-Bedrock נעשות בזהות ה-AWS של השרת, כלומר כל השימוש של כל הלקוחות מחויב בחשבון שלך. אל תפעיל בסביבה משותפת בלי מנגנון חיוב ללקוחות.
  2. אזור ומזהי מודלים (שלבים 7 עד 8).
  3. דומיין ותעודת HTTPS.
  4. סכומי תקציב אמיתיים. הערכים בקוד (100, 300 ו-1,000 דולר) הם דוגמאות.
  5. האם לבנות CloudFront. את SES מחברים כבר בפיילוט (שלב פ2).
  6. האם להוסיף סיבוב סודות אוטומטי.
  7. מתי לחבר שליחת מיילים אמיתית, ואז להפעיל REQUIRE_EMAIL_VERIFICATION=true.
  8. מעבר ל-verify-full עם תעודת ה-CA של RDS.

מה לא נבדק

  • בקשות ותשובות מול Bedrock החי, מזהי מודלים וזמינות לפי אזור.
  • pgvector על RDS עם PostgreSQL 16.
  • הרצת התמונות ב-ECS ובדיקות הבריאות שם.
  • שרת הדמו על EC2: התפקיד, ה-hop limit, GHCR והנפקת התעודה של Caddy מול דומיין אמיתי. פריסת ה-Compose עצמה נבדקת ב-CI.
  • גיבוי ושחזור של השרת היחיד, שליחת מיילים דרך SES, והעברת נתונים מהשרת היחיד ל-RDS.
  • אימות ל-ElastiCache, ושימוש בדלי S3 דרך תפקיד המשימה.
  • תפקיד ה-OIDC ל-GitHub וה-workflow של הפריסה.
  • AgentCore לא נבנה. הוא מתועד כמתאם אופציונלי בלבד.
